# GliDecide: GLiClass decision models on a MIMIC-IV knowledge graph

Companion code for **[Do Decision Models Follow the Evidence?](https://open.substack.com/pub/matheinated/p/do-decision-models-follow-the-evidence?r=ttco8&utm_campaign=post&utm_medium=web&showWelcomeOnShare=true)**

How well do the [GLiClass v4](https://huggingface.co/knowledgator/gliclass-v4-edge) decision models make decisions over a knowledge graph?
This folder tests Edge, 2B, 9B and 27B on 48 questions about a small clinical graph built from the openly available MIMIC-IV demo.

The main run gives the model a graph excerpt as text, a set of decision rules and a list of candidate answers. The model picks one. Other runs vary the evidence, rules and answer wording.
The setup follows the [knowledge-graph reasoning example](https://huggingface.co/knowledgator/gliclass-v4-edge#knowledge-graph-reasoning) in the Edge model card:
graph facts and rules are the input text, the question is the prompt, and the candidate answers are the labels.
Each candidate answer in `questions.json` has a `label`, such as `SOME_ADMISSIONS`, and a `description`; a run shows the model one or the other.

The graph’s node types, relationships and fields are documented in [mimic-schema.json](mimic-schema.json).

## The questions

All 48 questions are about the same four patients, the only patients in the graph, and each has one correct answer.

- **Q01–Q22** have gold answers derived from the graph with the decision rules. Each comes with the Cypher query that checks its gold answer, and the query's output.
- **Q23–Q30** are twins: copies of an earlier question (`variant_of`) with edited evidence, to test whether the answer follows the evidence. Their graph text is not original MIMIC data.
- **Q31–Q40** depend on the meaning of text in graph nodes, such as a drug class or an organism type. Their gold answers were proposed by Claude from the standard clinical meaning of the recorded names and checked by the author against the WHO ATC index, ICD-9-CM/ICD-10-CM code titles and MedlinePlus.
- **Q41–Q47** use lab results and the date of death: potassium, platelet, sodium and creatinine results against their reference ranges or a threshold, a creatinine trend, and death within 30 days of discharge. Q41, Q43, Q44, Q45 and Q47 come with their Cypher queries and outputs. Q42 is a twin of Q41 with a value at the limit of its range, and Q46 depends on the meaning of a diagnosis, like Q31–Q40.
  Q44 counts lab results that are linked to the patient but not to the admission: in this graph, 254 of the 1,264 lab results drawn during the eight stays, from emergency department registration to discharge, have no admission link.
- **Q48** is a twin of Q17 with the same nodes and rewired edges, so only the relationships change, and with them the correct answer.

Each question carries its decision rules. R01 limits the patient facts to the supplied evidence; R10, used by Q31–Q40 and Q46, permits general clinical knowledge of what drug and diagnosis names mean; R12, used by Q41–Q46, defines when a lab result is above or below its reference range.

`question_type` says what each question tests: `lookup` (5), `graph` (13), `computation` (16) or `semantic` (14).

### The runs

Every model answers every question seven ways. The run name is part of each result file name: `results/<model>_<run>.json`.

| Run | Model input | Answer options shown | What it tests |
|---|---|---|---|
| `label_graph` | graph excerpt + rules + question | labels | The main test of answering from the graph |
| `label_nograph` | rules + question | labels | Abstention when the graph is withheld |
| `description_graph` | graph excerpt + rules + question | descriptions | Sensitivity to answer wording |
| `label_noedges` | node information + rules + question | labels | Sensitivity to removing relationship lines |
| `label_norules` | graph excerpt + question | labels | Sensitivity to removing decision rules |
| `label_nograph_norules` | question only | labels | Abstention with both graph and rules withheld |
| `description_nograph_norules` | question only | descriptions | Sensitivity to answer wording when evidence is absent |

Runs with graph excerpts are scored against each question’s expected answer. This includes the runs with edges or rules removed.
For all three runs without the graph, the expected answer is `INSUFFICIENT_INFORMATION`.

Removing relationship lines leaves node properties, including record identifiers, available to the model.
Q17 and Q48 then have identical inputs even though their expected answers differ.
Removing rules also changes what can be established from the supplied instructions, particularly for Q06, Q09, Q11–Q14 and Q26–Q30.

## Setup

Use Python 3.12 and uv. Download and extract the `Blogs_Content` repository, then open a terminal in its `gliclassv4_on_graphs/` folder.
Keep `pyproject.toml` and `uv.lock` beside the notebooks. [Install uv](https://docs.astral.sh/uv/getting-started/installation/).

```bash
uv sync --locked
```

This creates `.venv` and installs the locked dependencies, including the notebook kernel and matplotlib.
Open the notebooks from this folder in your notebook editor and select the Python interpreter in `.venv`.
The working directory for notebooks and terminal commands should be `gliclassv4_on_graphs/`. [uv environment setup](https://docs.astral.sh/uv/concepts/projects/sync/).

## Run Edge and 2B locally

Open [run_edge_2b_locally.ipynb](run_edge_2b_locally.ipynb) and run all cells. Both models run on CPU, one after the other; the first run downloads each model from Hugging Face.
2B is much slower than Edge on a CPU. Results are saved to `results/edge_<run>.json` and `results/2b_<run>.json`.
Rerunning a model replaces its matching result files.

## Run 9B and 27B on a GPU pod

The larger models run sequentially on a GPU. The default configuration uses a single RunPod H100 with 80 GB of VRAM.

Open [run_9b_27b_on_pod.ipynb](run_9b_27b_on_pod.ipynb), or run the same job from a terminal.

```bash
uv run run_on_pod.py
```

The job creates or reuses the configured pod, uploads `src/` and `questions.json`, installs the local versions of `gliclass` and `pandas`, and runs both models.
It downloads `results/9b_<run>.json` and `results/27b_<run>.json`, replacing matching local files.

Put your settings in a local `.env` file beside the notebook. Keep this file on your own machine.

```dotenv
RUNPOD_API_KEY=...
# Private key whose public key is registered with RunPod
RUNPOD_SSH_KEY=~/.ssh/id_ed25519
# Optional, for Hugging Face downloads on the pod
HF_TOKEN=...
```

The pod is billed while it exists. By default, the script attempts to terminate the pod and delete its volume in its cleanup step, including after errors or Ctrl-C.
The `--end stop` option retains the volume, and `--fresh` deletes an existing pod before creating another.
The GPU type, image and models are set in `POD` and `MODELS` in `run_on_pod.py`.

```bash
uv run run_on_pod.py --help
```

## The graph

The questions already carry the graph excerpts they need, so running the models needs only `questions.json`.
`mimic-graph.json` is the whole graph as plain JSON (`nodes` and `relations`), readable with any JSON tool.

The graph holds four patients from the [MIMIC-IV Clinical Database Demo 2.2](https://physionet.org/content/mimic-iv-demo/2.2/), drawn from 12 tables of its `hosp` module.
It has 12 node types and 20 relationship types, described in `mimic-schema.json`.
Every node is one row of a source CSV file with its original values, and relationships join rows on exact identifiers.

**Neo4j is optional.** It is only needed to explore the graph visually or to rerun the Cypher queries in `questions.json`.

### Rebuild the graph (optional)

The raw MIMIC-IV demo is not included here. To rebuild the graph from it:

1. Download the ZIP file from the [PhysioNet project page](https://physionet.org/content/mimic-iv-demo/2.2/) (open access, no credentialing) and unzip it into `data/raw/`.
   Keep `SHA256SUMS.txt` at `data/raw/mimic-iv-clinical-database-demo-2.2/`, alongside `hosp/`. The extractor accepts the original `.csv` or `.csv.gz` files and checks them against that manifest.
2. Extract the four patients from the 12 tables. The script checks every file against PhysioNet's checksums.

   ```bash
   uv run python -m graph_build.process_mimic
   ```

3. Build the graph. The scripts never overwrite existing files, so write the rebuilt graph next to the published one and compare them.

   ```bash
   uv run python -m graph_build.build_mimic_graph --output mimic-graph.rebuilt.json
   ```

### Load into Neo4j (optional)

`graph_build/mimic-graph-import.cypher` loads the graph with APOC; its header lists the requirements.
Copy `mimic-graph.json` into Neo4j's `import/` folder, set the file parameter and run the statements in order.

```cypher
:param graphFile => 'file:///mimic-graph.json'
```

## Results

Each entry is the number of correct responses out of 48. Higher is better.
For the three runs without the graph, the counts measure correct abstentions.
The other four rows measure agreement with each question’s expected answer.

| Run | Edge | 2B | 9B | 27B |
|---|---:|---:|---:|---:|
| `label_graph` | 22/48 | 24/48 | 36/48 | 38/48 |
| `label_nograph` | 20/48 | 29/48 | 8/48 | 7/48 |
| `description_graph` | 19/48 | 31/48 | 38/48 | 40/48 |
| `label_noedges` | 22/48 | 25/48 | 35/48 | 37/48 |
| `label_norules` | 21/48 | 26/48 | 36/48 | 35/48 |
| `label_nograph_norules` | 8/48 | 19/48 | 0/48 | 0/48 |
| `description_nograph_norules` | 27/48 | 27/48 | 1/48 | 6/48 |

These counts come from the supplied JSON results, scored with `src/evaluate.py`.
The question set is small and manually assembled, includes ten edited twin pairs, and covers four patients.
Treat these results as observations from this experiment. The results notebook provides the breakdowns and individual answers.
